# Project Operating Manual

## Purpose

This manual defines how a project runs inside Workstream. It is the practical bridge between a project guide and daily work.

Every project has:

- active guide
- queue owner
- reviewer owner when human review is required
- guide source snapshot
- guide sufficiency report
- submission artifact policy
- effective project submission artifact policy hash
- generated project pre-submit checker policy
- post-submit checker policy
- review policy
- revision policy
- contribution policy and published versions
- review guard when human review is required
- lessons learned log

## Project Setup Checklist

Target v0.1 checklist before releasing tasks. The
[capability ledger](roadmap_status.md) distinguishes delivered behavior from
remaining setup/activation work:

- project name and slug exist
- project guide metadata created with at least one ordinary-text task example and
  the complete PDF/DOCX/PPTX or UTF-8 Markdown (`.md`) document list
- every declared original uploaded to ArtifactStore/S3 using its returned document ID
- automatic setup starts after all declared documents have committed bytes
- project owner setup material captured
- latest project setup run visible through covered Project Manager or authorized
  Operator/Audit projection
- active ContributionPolicy configured with its current published version
- explicit `accepted_submission` and `completed_review` rules configured as
  compensated or unpaid
- allowed task types listed
- task source, description, acceptance, and rejection fields listed
- guide sufficiency report passed or warnings acknowledged by an authorized
  covered Project Manager
- complete unified proposal is available for Project Manager review and
  artifact/pre-submit approval; manual provenance cannot impersonate or edit
  agent-derived output
- effective project submission artifact policy hash persisted
- generated project pre-submit checker policy is created from the effective project submission artifact policy
- project pre-submit checker bundle hash persisted
- post-submit policy is projected from the same unified compilation after
  upstream approval; it triggers no second guide inference or work evaluation
- generated project post-submit checker policy compiled and all pre/post
  capability-gap dispositions resolved; explicit approved human-review
  requirements are valid non-gap classifications, not an automatic fallback
- compiled project post-submit checker policy attached with source/effective/pre-submit provenance
- current compiled project post-submit checker policy approved by an authorized
  covered Project Manager; a correction request supersedes and retains the
  compiled or already approved policy through a separate operation, preserving
  its evidence and requiring a new unified generation and separate reapproval
- review policy attached
- revision policy attached
- exact expected published, complete, binding-valid ContributionPolicyVersion
  validated against the active policy selector and bound atomically at guide
  activation
- reviewer pool assigned when locked `human_review_required=true`
- review guard created from the project guide when human review is required
- guide version marked active
- each task locks the guide snapshot, effective project submission artifact policy hash, and pre-submit checker bundle hash before entering `READY`

The existing versioned ReviewPolicy setting `human_review_required` defaults
true. False can activate when the approved guide has supported exact PRE/POST
checkers and no `human_review` requirement disposition. The selected production
completion route uses the authorized FinalAcceptance/CON operation after passing
required checks; new economic effects require an Operator-authorized live REV
generation. Activation itself does not start REV or silently switch the setting
to true.
Make REV live before false-policy production completion. A known non-live refusal
before routing effects uses the shared OUTBOX bounded retry after rollback;
attempt exhaustion dead-letters and has no automatic reopening. Other uncertain
delivery failures remain UNKNOWN.

Guide creation freezes the declared document set internally; there is no separate
public source-snapshot creation step. The internal guide source snapshot freezes the declared document metadata and
the guide task-example hash/count commitment. While the guide is
still draft, an authorized covered Project Manager may attach or update review
and revision policy records after snapshot capture because those records are
activated as separate guide-policy context. Contribution policy is project-level
and independently published by its owning authority. Checker policy records are
generated by Workstream setup and exposed as generated setup output.

Publication never silently changes an active attempt. After a human
`needs_revision`, revision preparation compares the complete applicable active
guide and policy context and atomically rebases every changed valid component,
including the task-governing ContributionPolicyVersion, for the next attempt. The
completed ReviewLease and all prior history remain immutable.

An authorized Project Manager reviews the complete bounded proposal before
approval. Effective intake combines mandatory platform defaults with approved
project rules using the canonical CHECKERS compiler. Post-submit policy is a
separate deterministic projection of the same unified result; no contributor-work
evaluator runs during setup or approval.

Inference drafts a private structured candidate, then checks coverage against the
originals in a fresh model context. Every draft, review and correction must pass
strict schema, canonical, owner-context and source validation. Every phase must
initially read every assigned original, including for blocked proposals; searches
alone do not establish that observation. At most two known-invalid-output
corrections per phase share the original attempt limits. Only the validated final review
can become a retained proposal; failed review never publishes the private draft.
This does not replace the PM's review of source coverage and the proposed checks'
observable evidence.

For every newly compiled requirement, review `classification_rationale`. A
supported PRE/POST requirement or capability gap also has one typed
`check_specification` describing its evaluation method, execution mode and
duration, inputs, ordered checks, pass conditions, coded work findings,
positive/negative cases, runtime dependencies and infrastructure failures. PRE
means the complete check can reliably finish within 60 seconds before Submission
creation, even if durable execution and polling are used. Longer or model-based
work belongs to background POST. Automation by itself does not select POST.

| Specification field | Manager and engineering review question |
| --- | --- |
| `evaluation_method`, `execution_mode`, `maximum_duration_seconds`, `stage_rationale` | Is this static inspection, isolated execution or model evaluation, and does its complete work fit the proposed PRE/POST stage and budget? |
| `inputs` | Are all required package, manifest, request-metadata, file, directory or context inputs named and actually available to the runtime? |
| `check_steps`, `pass_conditions` | Can an implementer build the ordered evaluation and tell unambiguously when it passes? |
| `failure_findings` | Does each work failure have a stable code, level, condition and contributor-safe message? |
| `positive_tests`, `negative_tests` | Do representative successes and plausible failures discriminate the intended behavior, with negative cases tied to exact finding codes and verdicts? |
| `runtime_dependencies`, `infrastructure_failures` | Are tools and services assigned to the current runner, checker implementation or a visible runtime gap, and are non-work failures kept outside contributor verdicts? |

The capability suggestion for a missing implementation points back to this
requirement and stage; it does not duplicate the specification in free prose.

Confirm that each claimed input is available to the selected runtime. The
ordinary checker image is offline and receives verified package material,
manifest, approved configuration and normalized request metadata. Task or guide
context, a model service and nested sandboxing are dependencies that must be
explicitly supplied; setup cannot invent them. Missing registered implementations
remain engineering gaps and must not be relabelled as human review. Workstream's
default covers only bounded ZIP safety, received-byte/manifest identity,
high-confidence secret detection and unchanged-work detection. Required files,
layout, project metadata and project-specific content rules still need project
checks even when the artifact policy records those rules.

### Manager-authored guide rules

An operator may select the provider-free `manager_authored` runtime
(`WORKSTREAM_PROJECT_AGENT_RUNTIME=manager_authored` with
`WORKSTREAM_PROJECT_AGENT_MODEL_PROVIDER`, `..._MODEL_API` and `..._MODEL` all set
to `none`). The compilation then runs no inference: the Project Manager
supplies the compilation result in a rules document uploaded with the guide.
The rules can come from a person, a deterministic generator or any AI tool
outside Workstream. Workstream treats them exactly like model output.
The rules document is an ordinary guide original, so every reader of the
locked guide, including contributors, can open it; keep internal notes out of
it. The hosted release guide describes the provider-key file requirement;
manager-authored compilation itself makes no inference call. All document reads
use the same isolated parser and exact source-access custody.

The runtime identifies the rules document by content, because guide manifests
carry no source filenames and JSON is not an admitted guide media type:

- Declare it as `text/markdown`. Label it `workstream-rules.json` so people can
  find it.
- Its whole UTF-8 body must be one JSON object whose `format` is
  `workstream.project_guide_rules.v1`.
- Exactly one guide document may match. None, two, or an invalid body ends the
  attempt as invalid output with failure code `schema_invalid` (or
  `unsafe_text` when prose fails the shared safe-text rule). Fix the rules and
  create a new guide version; the failed attempt is not retried.

Besides `format`, the object has exactly the result fields `status`,
`findings`, `submission_artifact_policy`, `requirements`,
`pre_submit_bindings`, `post_submit_bindings`, `capability_suggestions` and
`setup_notes` in this explicit manager-authored format. Inferred setup output has
no notes field and cannot classify human-review or project-management requirements. The
runtime adds `agent_name`, `agent_version` and `schema_version`. Each evidence
reference names a document by `"document"`: either its `sha256:` digest or its
manifest filename (`<source_item_id>.<extension>`), plus optional `start_page`,
`end_page` and `section`. The runtime resolves it to the exact source item and
document version, and also cites the rules document itself on every finding,
requirement and suggestion, so each item may carry at most 19 authored
references. A ready result must cite every other guide document at least once.

```json
{
  "format": "workstream.project_guide_rules.v1",
  "status": "draft_ready",
  "findings": [
    {
      "severity": "info",
      "code": "guide.ready",
      "message": "The guide states the deliverable and its review criteria.",
      "evidence_refs": [
        {"document": "sha256:<64 lowercase hex of guide.pdf>", "start_page": 1, "end_page": 2}
      ]
    }
  ],
  "submission_artifact_policy": {
    "maximum_file_size_bytes": 1000000,
    "maximum_package_size_bytes": 10000000,
    "required_artifacts": ["submission"]
  },
  "requirements": [
    {
      "requirement_id": "reviewer_checks_rubric",
      "statement": "A reviewer checks the submission against the rubric.",
      "disposition": "human_review",
      "classification_rationale": "The guide explicitly assigns this qualitative decision to an authorized human reviewer.",
      "evidence_refs": [{"document": "sha256:<64 lowercase hex of guide.pdf>", "section": "Rubric"}]
    }
  ],
  "pre_submit_bindings": [],
  "post_submit_bindings": [],
  "capability_suggestions": [],
  "setup_notes": []
}
```

New manager-authored results follow the same completeness rules as provider
results: every requirement needs `classification_rationale`, and every supported
or missing PRE/POST check needs one complete `check_specification`. Human-review,
platform-covered, lifecycle-policy and guide-blocker requirements omit the
specification. Capability gaps use `draft_ready_with_warnings`; they do not make
an otherwise sufficient guide `guide_blocked`, but activation remains unavailable.
Both PRE and POST binding parameters must conform exactly to the selected
registry configuration schema.

Historical results remain byte- and hash-stable. Reads and recovery omit the new
members when an older retained result did not contain them; they never synthesize
a rationale or specification. Strict completeness applies to newly compiled
results before persistence and projection.

The runtime opens every assigned original once through the attempt's exact
document grant and records each read. It allocates no provider container or
file, so each read is recorded without a provider attachment; the database
accepts such a record only for an attempt whose stored provider is `none`, and
refuses provider allocations for such an attempt. The stored attempt
configuration shows `manager_authored` and `none`.

A correction request on a manager-authored proposal is refused with
`correction_unsupported` (409), because a correction reason cannot change rules
taken verbatim from the document. Upload revised rules in a new guide version
instead. A transient read, timeout or storage failure is not an uncertain
provider outcome for this runtime: the attempt returns from
`compilation_provider_uncertain` to `compilation_reserved` and the next delivery
retries it. Cancellation reopens the attempt before it propagates. A fence left
by a crashed process reopens on a later delivery once the run deadline
(`timeout_seconds` plus `cleanup_timeout_seconds`) has passed, and setup
continuation keeps such attempts eligible for redelivery. A retried run reuses
the read records of the failed run. The database allows the return only for an
attempt whose stored provider is `none`; hosted attempts keep the one-way
fence. The hosted prompt-size limit (`maximum_manifest_bytes`) does not apply,
because no prompt is built. Only the first
matching rules document stays parsed in memory; later matches are recorded as
duplicates without their bodies.

## v0.1 Quality Gates

### Project Activation Gate

A project cannot become active unless guide, immutable guide-source snapshot,
passed or acknowledged guide sufficiency report, approved submission artifact
policy, persisted effective project submission artifact policy hash, project
pre-submit checker bundle hash, approved project post-submit checker policy,
review policy, revision policy, and the current published version of the active
`ContributionPolicy`, with exactly one explicit compensated/unpaid rule
for each of `accepted_submission` and `completed_review` are present. Guide
policy activation and contribution-policy publication remain independently governed,
but project activation requires both. Compiled
post-submit setup output carries exact source/effective/pre-submit provenance,
but activation remains blocked until the current compiled policy is approved
through the separate approval operation (AUTH-12G authority and POL-06B public API). A correction request can supersede either a compiled or an
already approved policy while its setup is current. It preserves the original
body and receipts and requires a new unified generation and separate reapproval;
it does not satisfy activation. A task cannot enter `READY` until it also locks the guide
source snapshot id/hash, effective project submission artifact policy hash,
project pre-submit checker bundle hash, and approved provenance-matched project
post-submit checker policy reference.

### Task Screening Gate

The existing create, screen and release APIs use exact Project Manager authority.
Send one UUID `Idempotency-Key` for each command and retain it for lost-response
retries. Creating a draft does not require an active guide. Screening locks the
approved active guide; release validates those frozen policies and requires a
nonblank decision reason. A receipt does not preserve authority after revocation.
Task-state changes prevent stale replay; a newer guide does not replace the
policies already locked onto the task.

CP08 enforces the guide-bound ContributionPolicyVersion lock before `READY`
and carries it through TaskAssignment and Submission. ReviewLease propagation
remains planned. See [the capability ledger](roadmap_status.md) for delivered
boundaries and remaining work.

A task cannot move to `READY` until the task contract is complete, the guide
version is locked, submission artifact requirements are clear,
checker/review/revision policy versions and the guide-bound
ContributionPolicyVersion are locked, and a release decision is recorded. A
task cannot become `READY` without that policy lock. TaskAssignment and
Submission later carry it for the exact attempt. When canonical review admission
is delivered, ReviewLease must copy the immutable Submission stamp without
current-policy lookup.

After screening and release, contributors use
`GET /api/v1/tasks/{task_id}/work-context` for the locked guide and lifecycle
context and `GET /api/v1/tasks/{task_id}/submission-requirements` for the exact
artifact, evidence, storage, packaging, hash, and attestation requirements.
Covered Project Managers use
`GET /api/v1/projects/{project_id}/tasks/{task_id}/work-context` for their
canonical exact-project projection. Work context now returns separate contributor
and manager task facts, the exact historical guide, review/revision references
(`policy_id`, `generation`, `policy_hash`), and the locked
`contribution_policy_version_id`. It omits obsolete payment amounts and
submission/precheck flags. Contributor `lifecycle.next_actions` contains only
currently applicable claim hints; management has no contributor lifecycle.
Executing a hint always rechecks authority. Locked policy provenance uses three
separate reads (all prefixed by `/api/v1`):

- Project Manager: `GET /projects/{project_id}/tasks/{task_id}/locked-context`,
  requiring a covering project/system Project Manager grant.
- Operator: `GET /operations/projects/{project_id}/tasks/{task_id}/locked-context`,
  requiring a system Operator grant.
- Audit Authority: `GET /audit/projects/{project_id}/tasks/{task_id}/locked-context`,
  requiring a covering project/system Audit Authority grant.

Management returns exact guide/policy references and the bounded post-submit
checker summary. Operator and Audit Authority return references only. All three
validate the task's original activation custody, including after guide replacement.
They require complete valid locked context in every task state; incomplete or
corrupt context returns 422. Missing, foreign-project and unauthorized reads
return the same 404. Caller token claims and task creation history do not
authorize these reads.
The old task-only locked-context route is removed.

### Bounded task history

`GET /audit/projects/{project_id}/tasks/{task_id}/evidence` requires a current
covering project/system Audit Authority grant. Project Manager, Operator, Finance
Authority, Access Administrator and Submitter roles alone cannot use it, even
where their permission catalogue contains `audit.read`.

The page contains only stored event identity/type, status transition, actor ID,
timestamp and validated assignment/authorization-decision references. Private
payloads, reasons, claims, external identities and policy bodies are excluded.
All task states, including an unbound draft, are inspectable. `limit` defaults to
50 (maximum 100). To continue, JSON-encode the returned `next_cursor` object into
the `cursor` query parameter. Each page checks current authority again; the
cursor is a position, not permission or an export snapshot. Wrong-project,
missing and unauthorized requests return 404; malformed cursors or invalid
stored evidence return sanitized 422. The old `/tasks/{task_id}/audit-events`
route is removed. Submission recovery retains its separate internal evidence reader.

### Submission Quality Gate — Current Boundary

Hidden durable post-submit execution and unfinished-attempt recovery use exact
input, execute and finalize authority. PILOT-04 registers selected production
request and completion delivery. Required checks run against the exact Submission
version and artifact hashes before a passing result routes to `review_pending`
under a true ReviewPolicy or the shared authorized FinalAcceptance under a false
ReviewPolicy. Contributor-correctable failures retain the exact remediation cause.
ARCH-04F4 provides a hidden, reason-bound `operations.checker.retry` command for
an exact current terminal `infrastructure_failed` run; it creates a new CHECKERS
generation through the existing request handler without changing the failed run.
There is no public checker-retry route. Infrastructure failure does not move a
Submission directly to human review.

External origin qualification and webhook drop notifications are future adapter concerns, not v0.1 gates.

## Review, approve or correct a guide proposal

Poll the existing guide setup status until `finalized_compilation_id` is present.
An invalid or uncertain provider outcome has no finalized proposal to approve or
correct; it cannot be restarted through correction. For a ready or blocked
finalized result, use this prefix:
`/api/v1/projects/{project_id}/guides/{guide_id}/compilations/{compilation_id}`.

| Method and suffix | Purpose |
|---|---|
| `GET /proposal` | Read both proposals, findings, suggestions and the exact target |
| `POST /pre-submission-approval` | Approve the displayed pre-submission target and warning acknowledgements |
| `POST /corrections` | Record feedback and allocate one successor without invoking the agent |
| `POST /corrections/{correction_operation_id}/dispatch` | Explicitly run that successor asynchronously |
| `GET /post-submission-policies/{policy_id}` | Inspect the complete derived policy, lineage and saved correction |
| `POST /post-submission-policies/{policy_id}/approval` | Separately approve that displayed policy |
| `POST /post-submission-policies/{policy_id}/corrections` | Request a unified successor from that policy |

All these operations require a current human Project Manager grant for the exact project.
Audit/Operator authority and a system-scoped manager grant do not grant proposal
access. The source pointer is not permission to read another project's proposal.

Approval and correction require exactly one UUID `Idempotency-Key` header.
Duplicate occurrences are rejected with 422, even when their values match. Copy the exact
`target` from the package into the request body; do not construct it from status
summaries. Pre-submission approval supplies `acknowledged_warning_hashes` from that package and,
when replacing a prior approval, both prior approval identifiers. Correction
supplies a meaningful `reason`. The body has no second idempotency key. Dispatch
uses the committed correction operation ID for stable replay identity.

If the correction creation response is lost, an authorized replacement manager
can read `/api/v1/projects/{project_id}/guides/{guide_id}/setup-runs/latest`.
For a correction successor, that response supplies `correction_operation_id` and
`predecessor_compilation_id` together. Use the predecessor as `{compilation_id}`
in the dispatch prefix above, and the correction ID in its dispatch suffix.
A `correction_requested` successor waits for this explicit dispatch. Both pointers
remain available after dispatch and finalization; neither grants proposal access
or bypasses current Project Manager authority. Initial setups have neither pointer.

After pre-submission approval, poll `GET /proposal` for `post_submit_policy_id`.
A null ID means derivation has not produced a policy for that exact compilation.
The fixed setup worker derives from the saved result without another model call.
Every 60 seconds, Beat scans committed approvals missing a derivation; bounded
pages progress past unavailable candidates. Broker failure leaves approval
committed and recoverable. No public derive endpoint or extra manager action is
needed. Current authority and exact upstream/catalogue custody are rechecked on
every delivery. Stale custody requires a new corrected generation and approval;
it is never relabelled by recovery.

Use the discovered policy ID with the three post-submission-policy suffixes.
Copy that read's `target` into the separate approval or correction body;
correction also includes `reason`. Both require exactly one UUID header key.
The read includes the complete canonical `policy`, `lifecycle_status`, `current`,
its approval operation ID and any canonical correction receipt. Dispatch uses
the shared predecessor-compilation route above, including after manager handoff.

Pre-submission approval atomically persists the existing artifact/effective/pre-submit chain.
It does not approve the post-submit policy or activate the guide, and makes no
model call. Correction leaves finalized history immutable. Dispatch commits its
request and queue intent before broker publication; failed publication remains
recoverable through the existing continuation scan. Repeating dispatch cannot
create another attempt or bypass the one-shot provider fence. Poll setup status
for completion; dispatch returns only the correction/setup identity and status.

Authority or selector failures are concealed as 404; stale targets, blocked
approval and conflicting replay are 409; malformed requests are 422; storage
unavailability is 503. Refresh the exact proposal before resolving a conflict.
