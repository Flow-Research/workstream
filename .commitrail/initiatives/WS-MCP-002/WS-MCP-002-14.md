# WS-MCP-002-14 — Single-use authorization for remote MCP ZIP submissions

- Initiative: WS-MCP-002
- Durable disposition: Complete
- Intended merge outcome: Record an implementation-ready design for authenticated MCP issuance of one-use ZIP submission credentials, preserving the consolidated submission operation; no runtime capability is enabled by this design change.

## Intent

A contributor's agent has its ZIP in an external execution environment. The
remote MCP service cannot open that filesystem, and large archives must not be
encoded into model-visible JSON arguments. The user selected an authenticated
MCP authorization request followed by one raw-ZIP API request using a temporary,
single-use credential restricted to that submission. The ordinary Workstream
API access token remains inside the MCP service.

## Design and decisions

The [complete contract](../../../docs/spec_mcp_submission_upload.md) belongs to
the existing MCP initiative and depends on the current single-request submission
contract. Its decisions are:

- Replace `workstream_submission_create` with metadata-only
  `workstream_submission_upload_authorize`; the client streams its own local
  file to the existing raw-ZIP endpoint using a custom `SubmissionUpload` header.
- AUTH owns the ten-minute, digest-only credential and a distinct submission-only
  context. Issuance uses normal Flow authentication; reserve/acceptance evidence
  retains the exact issuing grant and credential provenance.
- One actor/key record rotates only while unused. T1 commits consumption with
  operation, task guard, capacity and reserve allow atomically. Consumed keys
  never receive another token; current authenticated operation reads recover
  uncertain outcomes and terminal attempts require a new key.
- Exact feedback/count/hash bind the token to the requested ZIP; stream, repository
  and SQL guards compare actual source identity before EOF seal and PRE.
- Private continuation evidence permits the original in-flight request to finish
  or observe its receipt without granting public read/replay authority. Later
  PRE/T4 checks preserve existing locks and fresh exact-grant authority.
- A trusted public HTTPS origin supplies the descriptor destination. The scoped
  token appears once in structured output; ordinary OAuth credentials remain
  internal. Unrelated bounded document/import transfers stay supported.

The implementation map covers API composition, AUTH/schema/audit, ART streaming
and recovery, MCP packaging/configuration, hosted ingress and documentation.
U01–U27 specify future public, SQL, transaction, concurrency, storage, installed
client and operational proof; none is presented as executed by this design PR.

## Review findings

Source inspection resolved three concrete risks before the formal plan review:
credential-row actor IDs cannot be turned into a Flow-authenticated human
context; a newly active Submitter grant cannot revive a credential issued under
a revoked grant; and current foreground public-read calls need explicit private
continuation/receipt evidence for credential mode. The public upload origin and
SDK structured-result validation/duplication rules are also explicit in the spec.

Focused plan review produced these resolved design changes; final target-bound
review verdicts remain session/PR evidence rather than product authority:

- `ARCH-REUSE-001`: ordinary Flow new admission now checks the same credential
  key reservation through AUTH. A shared actor fence and fresh SQL conflict read
  enforce both creation orders; existing admitted-operation read/replay remains.
- `SEC-001`: explicit issuer/subject rate controls and a retained per-assignment
  64-key/256-generation budget prevent authorization-only history growth. U26
  covers concurrency, SQL bypass, refusal and the final lost-response recovery
  limit, without deleting evidence or exposing general API credentials.
- `SEC-002`: U27 names independent-session revoke-first and boundary-first proof
  at T1, PRE and T4, preserving committed acceptance after later revocation.
- `DOC-MCP-UPLOAD-001`: expiry is an admission deadline, including lock waits;
  starting the HTTP request before expiry does not extend credential validity.
- `DOC-MCP-UPLOAD-002`: all PRE, terminal-failure and replacement guidance is
  conditional on remaining issuance budget and points to the same explicit
  independently authenticated fallback at exhaustion.
- `DOC-MCP-UPLOAD-003`: the Complete design record retains the actual revised
  candidate check result; subsequent exact-head results belong in the PR.
