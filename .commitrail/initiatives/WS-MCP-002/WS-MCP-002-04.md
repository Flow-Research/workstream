# WS-MCP-002-04 - Administrative grant mutations

- Initiative: `WS-MCP-002`
- Durable disposition: `Complete`
- Intended merge outcome: Add two fixed public-API grant mutation tools to the independent MCP adapter.

## Intent

Let authorized human Access Administrators issue and revoke administrative grants
through MCP while Workstream remains the sole authority and replay owner.

## Current behavior

Main at `3b9fbf64` exposes the authoritative issue and revoke operations in
`backend/app/modules/authorization/router.py`. The API owns token verification,
current authority, self-action guards, target concealment, duplicate detection,
last-administrator protection, idempotency state, transactions and audit evidence.
Before this chunk, the merged adapter had nine read/self-service tools and no
grant mutation binding. This chunk raises the completed catalogue to eleven tools.

## Design and decisions

Expose exactly `workstream_admin_grants_issue` and
`workstream_admin_grants_revoke`. Inputs use closed typed `arguments`: a UUID
`idempotency_key`, the exact API body, and a UUID `grant_id` for revoke. The key
is forwarded unchanged only as `Idempotency-Key`; incoming MCP HTTP headers and
`_meta` cannot provide or override it. Reasons preserve exact caller text after
1-500 UTF-8 byte and NUL validation. Role/scope shape is rejected before dispatch,
but Workstream still decides who may perform the operation and whether current
state permits it.

Each call makes one fixed POST and accepts only its exact HTTP status and receipt
semantics: issue is `201`/version 1 and revoke is `200`/version 2. A revoke receipt
must also identify the requested grant by UUID identity. Explicit API denials preserve
only approved status/code/correlation data. Timeout, transport failure, 5xx,
unexpected success, malformed success or a foreign revoke receipt after dispatch
returns `workstream_execution_uncertain`; the adapter never claims rollback and
never retries. Recovery repeats the same arguments/key, including after adapter
restart, and Workstream returns the durable replay.

## Acceptance criteria

- [x] Exactly eleven tools and zero resources/prompts; both new schemas are closed.
- [x] Valid calls perform one exact POST with unchanged body, caller bearer and key.
- [x] Missing/invalid keys, UUIDs, scope combinations and UTF-8 reason bounds reject
  before dispatch; HTTP headers and MCP metadata cannot substitute tool arguments.
- [x] Safe API denials preserve status/code/correlation without private diagnostics.
- [x] Ambiguous execution is non-retryable and the adapter performs no automatic retry.
- [x] Revoke accepts only a receipt for the requested grant UUID; a foreign receipt is
  uncertain after exactly one dispatch, while equivalent UUID spellings remain valid.
- [x] Selected contracts match current full-app OpenAPI and ship in the built wheel.
- [x] Real isolated PostgreSQL 16 proof covers replay across adapter restart,
  ordinary/self denial, issue/revoke mismatch and authority removal; CI reruns it
  from the built wheel as a required PR check.

## Review findings

The implementation follows the current backend OpenAPI rather than the older HTML
success wrapper. The HTML remains naming/input/annotation design evidence; runtime
results preserve the backend's bounded `AuthorityMutationResponse` directly, matching
the existing adapter convention. Shared gateway success handling now accepts an
operation-specific expected status without changing existing read/profile behavior.

Local focused review found no need to copy Workstream authorization policy into the
adapter. Only public request-shape constraints are validated locally. The real
integration test recreates the adapter between issue and replay, proving that replay
state belongs to Workstream, then checks current authority after a delegated Access
Administrator grant is revoked.
