# WS-MCP-002-02 — Own profile editing and project authorization context

- Initiative: `WS-MCP-002`
- Durable disposition: `Complete`
- Intended merge outcome: Add two caller-owned MCP tools for profile editing
  and exact-project authorization context, preserving Workstream as the only
  authorization and lifecycle authority.

## Intent

Complete the adapter's bounded self-service surface. A caller can update only
their editable profile fields and inspect only their effective authority for one
project through the existing public Workstream APIs. The adapter forwards the
caller's request bearer and never calculates roles, grants or permissions.

## Current behavior

PR #418 delivered the independently packaged `workstream_profile_get` foundation.
Current backend main exposes strict `PATCH /api/v1/actors/me` and
`GET /api/v1/actors/me/authorization-context?project_id=...` contracts in
`backend/app/api/routes/auth.py`. Workstream owns token verification, actor
resolution, profile normalization, project concealment and current authority.

## Design and decisions

`workstream_profile_update` accepts a closed object containing at least one of
`display_name` and `contact_email`. It preserves omitted fields versus explicit
nulls, applies the backend's trim/blank/NUL/length rules before dispatch, and sends
one unkeyed PATCH. Transport failure, upstream 5xx or an unexpected success/redirect
response after dispatch is uncertain execution; the adapter never retries it.
Explicit 4xx API rejections retain their safe status/code. The update tool is
marked potentially destructive because explicit null can clear an existing field.

`workstream_authorization_context_get` accepts exactly one bounded `project_id`
string and sends it as an encoded query parameter to the fixed context route.
Workstream returns current roles/actions or its concealed denial. The adapter
does not infer authority from the result or use it to authorize another call.

Both tools read the bearer from the MCP HTTP request, forward it unchanged, and
validate successful responses against selected current OpenAPI contracts. Tool
annotations do not claim side-effect-free reads because Workstream admission and
audit paths may write state.

## Review findings

The first focused review found valid gaps in response format checking,
uncertain PATCH response handling with correlation, missing input/revocation
tests, and stale continuation wording. The implementation now validates UUID
and strict RFC3339 date-time formats through the pinned maintained validator,
reports malformed successful PATCH responses as
non-retryable uncertain execution, covers all named zero-dispatch boundaries and
grant-revocation concealment, and points continuation to WS-MCP-002-03. Exact-head
review replay and hosted checks remain transient PR evidence.

Final review also covered proxy-generated HTTP errors after a possible commit:
these preserve uncertainty and never advertise the unkeyed PATCH as retryable.
Regression cases simulate a write followed by 5xx or an unexpected HTTP response,
retain explicit API rejection behavior, and reject excessively nested JSON safely.

Maintainer review strengthened the real-process proof: first set a non-null
contact email, then omit it while changing the display name, then explicitly
clear it. Each step checks both the MCP response and a direct API read of persisted
state. A focused integration test compares both editable fields with the actual
backend request model for trimming (including Unicode whitespace), preserved
interior spaces, null, blank and NUL rejection. This supplements OpenAPI drift
checks because schema snapshots do not capture those normalization rules.
These test-only refinements do not change the capability or roadmap boundary.
