# WS-CLI-001-13 — Approve exact pre-submission proposals

- Initiative: `WS-CLI-001`
- Durable disposition: `Planned`
- Intended merge outcome: Managers can deliberately approve the displayed intake proposal through the existing public POST, with exact caller-owned replay custody.

## Intent and design

CLI12 displays the complete proposal but cannot commit the manager's intake
decision. Add `workstream project guide approve-pre PROJECT_ID GUIDE_ID
COMPILATION_ID --input FILE --idempotency-key UUID`. The regular bounded JSON
file contains exactly the public `GuideProposalApprovalInput`: displayed
`target`, explicit optional `acknowledged_warning_hashes`, and optional paired
previous-approval operation/output selectors. Never fetch latest, auto-acknowledge
warnings, derive approval from a successful read, or change the input on replay.
Issue one POST to the public exact-compilation `/pre-submission-approval`.

Reuse the existing target wire type/validator, closed JSON decoder, bounded
regular-file input reader, UUID identity comparison, safe renderer and hardened
no-replay transport. Preserve omitted/default/null input semantics and send the
original JSON bytes. Validate target membership against all three path UUIDs;
reject malformed nested identities, hashes, acknowledgments or replacement
pairs before dispatch. Warning matching, currentness, policy validity and
authority remain backend decisions. Do not compute canonical business digests
or create another policy validator. Validate the closed receipt, record UUIDv7
identities, digests, artifact-policy identity and exact acknowledgment order.
JSON preserves the complete server receipt; text identifies this as intake
approval, not post-policy approval, activation or executed checking.

Use the existing 1 MiB input bound and common response limit/deadline. A lost,
oversized, malformed, substituted or noncanonical write response has unknown
outcome; explain manual replay of unchanged selectors, input and key. Canonical
4xx is a known rejection. Neither this command nor HTTP/2 retries may resend it.
The backend may publish post-policy derivation after commit; CLI success proves
only the immutable intake-approval receipt, not worker delivery or derivation.

Alternative rejected: one command that reads latest, accepts every warning and
approves/activates the chain would silently make manager decisions and introduce
stale-target races. No new abstraction, dependency or permission system needed.

## Scope

Allowed: new `cli/internal/api/guide_approval.go`,
`cli/internal/command/guide_approval.go`, registration in
`cli/internal/command/guide_create.go`, new process proof
`cli/tests/integration/test_guide_approval_http.py` and real API proof
`cli/tests/integration/test_guide_approval_public_api.py`; CLI/root README,
affected roadmap claims, this record, initiative overview and index.

Prohibited: backend/MCP/workflow/dependency changes, hidden routes, automatic
reads/retries/polling, correction, post-policy approval, guide activation,
provider execution, local permission/policy decisions, unit-test suite, skips,
coverage quotas, data deletion or new database fixture framework.

## Acceptance and verification

- Built-process HTTP proof: exactly one POST with unchanged input, bearer,
  retry key and escaped UUID selectors; compact selectors compare by identity.
  Closed validation handles required/null/default members and preserves large
  target generations. Reject missing key, target substitution, null/duplicate
  warning members, mismatched prior pair, duplicate/unknown fields locally.
- Receipt proof: reject malformed/missing/null/extra members, wrong artifact
  identity, non-v7 record IDs, invalid digests and changed acknowledgment list;
  never report write success or leak raw server errors. Exercise dropped reply,
  malformed canonical 4xx (`details:null`), redirect, reflected credential and
  HTTP/2 GOAWAY through existing adversarial process fixtures. Every uncertain
  result supplies the unchanged-input manual-replay hint and no automatic retry.
- `test_approval_public_socket_replay_and_fresh_authority`: reuse canonical
  `proposal_case` retained finalization fixture, a real API socket, real Flow
  verification, production AUTH and isolated PostgreSQL. Inspect the proposal
  first; confirm OpenAPI public exposure, successful exact receipt and unchanged
  replay, one stored approval/audit, and no activation. Missing/wrong warning
  acknowledgment and changed target deny without another approval. Store a
  foreign project for the substitution deny; outsider, revoked manager and
  suspended actor deny after valid controls, including replay after revocation.
  Arrange actor/grant through existing canonical fixtures, not HTTP overrides.
  The memory broker may acknowledge publication without a worker; distinguish
  this unclaimed delivery boundary from actual approval transaction proof.
- Falsification: remove the receipt artifact-identity comparison in an isolated
  scratch build and require the named response-substitution process case to
  fail at its success/unknown-outcome assertion.
- Run complete CLI process/API integration via `run_isolated_tests.py`, inspect
  cleanup, Go verify/tidy-diff/vet/build, Ruff/format, links/stale wording and
  Commitrail validation. Full backend completeness remains required hosted CI.

## Risk, reviewers and human focus

L1 authenticated manager mutation and untrusted response; no invented urgency.
Plan review first traces fixture feasibility and wire/default/replay semantics.
Then one clean review wave: architecture/documentation/reuse, security, and
QA/test-delta as three bounded assignments under the reviewer matrix. Lead runs
shared checks once; no ceremonial nine-reviewer fanout. Human review focuses on
deliberate warning acknowledgment, exact target/prior selection and the fact
that intake approval is neither post-policy approval nor guide activation.
