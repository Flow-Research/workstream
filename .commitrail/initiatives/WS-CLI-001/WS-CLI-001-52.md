# WS-CLI-001-52 — Prepare an initial ZIP in the contributor workbench

- Initiative: `WS-CLI-001`
- Durable disposition: `Planned`
- Intended merge outcome: Let contributors explicitly prepare an initial ZIP, inspect intake feedback and replay the exact preparation without creating a Submission.

## Intent

After the merged Claim/Start slice, the human asked to move forward. The next
bounded step is packaging/intake, not a second submission implementation or a
claim that the complete TUI journey is delivered.

## Current behavior

Main `517fe54c4` contains deliberate TUI claim/start. The existing typed
`api.Client.PrepareSubmission` streams one regular file, validates the packet,
returns intake feedback, checks source changes and supports explicit caller-key
replay. `task prepare` is its current consumer. Mine rows retain assignment IDs;
WorkContext confirms current-actor assignment but does not expose that ID.

## Bounded change

### Allowed

- Existing `cli/internal/tui/` model, rendering, request port and focused tests.
- Existing `cli/internal/api/submission.go` and its tests: an explicit optional
  expected SHA-256 argument to the same preparation operation, checked against
  its existing pre-send source hash. Update `command/submission.go` to pass no
  expected hash, preserving explicit CLI behavior; affected command test fakes.
- Focused native HTTP/public-API preparation tests and existing terminal fixtures
  only as needed, with unchanged strict defaults. Current CLI/design/roadmap and
  initiative/index documentation.

### Not allowed

Backend/API wire/auth/policy/storage changes; immutable Submission creation;
revision uploads or inferred predecessor selection; management, Review or awards;
polling, automatic POST retries, file execution, recursive file picker, automatic
UUID generation, generic operation journal, compatibility paths, CI weakening,
new dependencies or user-file writes.

## Design and decisions

- From fresh Mine Overview for an observed `in_progress` task, offer Prepare.
  On deliberate entry, freshly read exact WorkContext and require matching
  actor/project/task, assigned-to-current-actor and no revision context. Bind the
  selected Mine assignment ID; UI observations never replace backend guards.
- Use a compact staged form: regular ZIP path, exact optional summary and
  attestation, caller-owned UUID saved outside the session. Blank optional text
  means omitted; preserve printable ASCII text exactly and reject invalid input
  rather than trimming or silently converting it. Explain current API limits.
- Inspect/hash the selected regular file asynchronously, bounded at 512MiB, with
  cancellation checks and safe errors. No disk work on resize or row movement.
  Local paths support valid Unicode without control characters; the API's ASCII
  restriction applies to packet headers, not filenames. Use narrowly scoped
  platform-specific opening where required to reject nonregular sources without
  blocking the supported Linux, macOS or Windows terminal process.
  Confirmation shows exact actor/project/task/assignment, path, bytes, SHA-256,
  packet text and key. Only explicit save acknowledgment and `y` send one POST.
- Extend the existing shared preparation client with an expected SHA-256 input
  so a file changed after confirmation is rejected before dispatch. Retain its
  existing post-send source verification and unknown-outcome semantics.
  Verify the exact count and digest of bytes consumed by the request stream
  before confirming a successful receipt. Before/after file hashes alone miss
  a transient write restored before the final check. Synchronize body reading,
  closure and digest inspection; incomplete successful uploads remain unknown.
  A known denial may legitimately occur before reading the body.
  The expected hash is checked inside `PrepareSubmission` after its own first
  hash and before request creation, with a context cancellation check, not only
  in the TUI before a later independent hash. Open
  source handles inside commands, close on every path; no background descriptor
  stored in render state. No simulated upload percentage.
- Freeze the complete packet and file fingerprint for send/replay. Unknown
  outcomes prohibit replacement by a new packet/key; only explicit unchanged
  replay is offered. A replaced/changed file is not a replay. A local pre-send
  refusal must not erase an earlier uncertain server result. Pending work blocks
  navigation/duplicate dispatch; quit cancels the client, not server effects.
- Reuse existing bounded action outcomes/navigation/security clearing, extending
  operation-specific state only where upload inputs differ. No parallel generic
  mutation framework. Preserve the delayed-read401 dispatch guard from -51.
- Display ready admission separately from all non-ready storage states; include
  successful warnings and canonical blocking intake feedback. Every result says
  no immutable Submission was requested. No success on malformed/transport
  errors. Authorization denial clears protected text and disables replay while
  retaining only minimal inert recovery identities; never render bearer/errors
  unsanitized. Recover after restart through caller-saved exact inputs and CLI.
  Clearing a previously confirmed ready receipt must not relabel it not ready;
  report confirmed-but-cleared evidence without exposing the protected details.
- A ready receipt exposes its admission and exact packet for an inert CLI
  submission handoff, not an executable shell command or automatic submission.
  Do not claim historical preparation browsing or persistent recovery.

## Acceptance criteria

- Initial in-progress Mine task can prepare a real ZIP and display ready,
  non-ready and failed-intake results with findings; no Submission POST occurs.
- Cancel/resize/paste/navigation never sends implicitly. Corrected failed intake
  may start a new deliberately confirmed operation; unknown result cannot.
- Exact task/assignment/packet/key/hash are retained for explicit replay. A file
  modified after confirmation sends no POST; modifications during send cannot
  produce a confirmed success. Stale responses and delayed auth failures cannot
  reopen a write or restore protected content.
- Existing Claim/Start, reads, downloads, pagination and noninteractive CLI
  contracts pass unchanged. Text fields accept literal q and pasted content as
  text, never shortcut execution; bounded/plain/minimum rendering remains usable.
- Native built-binary HTTP tests assert ZIP bytes/headers, no automatic retry,
  failure/non-ready/unknown/changed-file/revoked paths. A signed public API native
  drill uses isolated PostgreSQL and existing artifact fixture to prove failed
  intake, ready preparation, exact replay, revocation and zero Submission rows.
  Storage fixture proof must not be labelled real S3; hosted MinIO proof remains
  separately identified. Run relevant Go tests/vet/race and full hosted checks.

## Risk and review routing

- Risk class: L1 (file input, contributor mutation, uncertain outcomes).
- Plan review before implementation; architecture/reuse, security, QA/test-delta,
  product/docs and CI-integrity if shared native fixture/selection is affected.
- Human focus: can a contributor identify the ZIP/packet, understand intake
  findings and distinguish preparation from submission without hidden actions?
- No new human decision is required by this bounded scope; no merge authorized.
- Size exception: the cohesive file-input operation needs model/API tests,
  native terminal wire proof and signed PostgreSQL owner proof together. This
  exceeds the preferred L1 diff size; no backend, schema or workflow changes
  are included. Review those proof layers separately against the same candidate
  rather than splitting the safety guards from the operation they protect.

## Evidence

Existing API/client/CLI proof is discovery evidence, not TUI runtime proof. New
focused tests must discriminate changed-file dispatch and implicit duplicate
requests, and preserve the existing signed/native Claim/Start tests. Exact-head
commands and reviewer results belong in the PR, not this durable record.

The signed native drill must construct an app from production Flow verifier
settings plus the fixture's exact ART namespace/local-store/scratch settings and
isolated database. Install only the fixture JWKS transport; leave DB/AUTH/TASK
owners unoverridden. If reused, name `LocalIntakeAdapter` explicitly as the
in-process guest-rule fixture, not sandbox execution. First send a canonical
failed-intake packet and assert feedback/zero Submission. Then use a fresh saved
key and valid ZIP/packet: pending verification -> direct invocation of the real
ART verifier -> exact native replay -> ready admission. Revoke through a
distinct signed manager and replay to prove fresh denial/clearing. POST
`put_attempt_id` is not GET preparation ID; the verifier consumes the former.
Do not invent a detail lookup or infer replay identity from the latest list row.
