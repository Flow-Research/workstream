# WS-CLI-001-10 — Upload a declared guide original

- Initiative: `WS-CLI-001`
- Durable disposition: `Complete`
- Intended merge outcome: Upload one declared guide document through the existing public API, returning a receipt bound to its exact original bytes.

## Intent

After CLI09 declares a guide, add `workstream project guide upload PROJECT_ID
GUIDE_ID DOCUMENT_ID --file FILE --media-type MIME --idempotency-key UUID`.
Use only the public keyed binary `POST /api/v1/projects/{project_id}/guides/{guide_id}/documents/{document_id}/content`.
Workstream owns authorization, membership, original custody, configured limits,
setup continuation and replay. This command does not approve or activate a guide.

Require explicit PDF, DOCX or PPTX media type matching the declaration. Open one
regular, nonempty file no larger than the existing 512MiB ART transport ceiling;
configured backend limits may be smaller. Hash the bounded original and stream
raw bytes through independent section readers on the same open descriptor with
exact Content-Length, not JSON,
multipart or base64. Do not buffer the whole file or infer MIME from its name.
Before confirming storage, recheck the open descriptor's size/modification time
and full bounded digest, including a byte beyond the original length. A changed
or unreadable source after dispatch fails with
guide_document_upload_source_changed, outcome_unknown=true and empty stdout;
the server may already have stored the original bytes. This is observation at
the confirmation boundary, not a filesystem lock or an immutable local snapshot.
File changes or server responses that disagree with the local SHA-256/size must
never report confirmed storage. Manual replay requires unchanged selectors,
file contents, media type and caller-owned key.

Reuse the existing hardened HTTP transport and binary-guide deadline (10-minute
total, 2-minute response-header bound). Extend its private request construction
for streamed bodies; retain current JSON request behavior. The total deadline
bounds HTTP transfer, not local file hashing. No preflight,
redirects, proxy, generated key, credential exchange or automatic transport
replay. One invocation sends at most one POST body, including HTTP/2 GOAWAY.

Require exact HTTP 202, bounded JSON and the closed five-field public receipt:
document_id, sha256, byte_count, status and replayed. Reject null/unknown fields
and substitutions; compare UUID identity, not spelling, and bind SHA-256/size
to the file. Only document_stored or object_confirmed establishes stored original
success; other well-formed statuses report an unconfirmed outcome, never guide
approval: guide_document_upload_unconfirmed, outcome_unknown=true, exit 1 and
empty stdout. A receipt with mismatching SHA/size instead reports
invalid_api_response with the same unknown-outcome exit/empty-stdout behavior.
Canonical 4xx remains a known denial; dropped, malformed, unexpected,
redirected or 5xx replies are unknown outcomes. Diagnostics never disclose a
credential, file path/content or raw provider/transport exception.

## Acceptance criteria

- Process tests capture exact raw bytes, Content-Type, length, bearer, key and
  supported UUID spellings; confirmed JSON retains the exact validated receipt and text
  is safely rendered. Invalid selectors/MIME/files send no request.
- Exercise file and response bounds, receipt UUID/hash/size/status/null/unknown
  substitutions, canonical and malformed 4xx, credential-reflecting metadata,
  redirects, dropped connections and HTTP/2 GOAWAY. Test the binary deadline
  separately from the ordinary JSON deadline. No automatic upload retry.
  Assert unconfirmed status and SHA/size mismatch each fail with exit 1,
  outcome_unknown=true and no successful JSON/text on stdout.
  Synchronize append, truncation and same-size overwrite (with restored mtime)
  after the server receives the original body and before its valid receipt;
  none may report success. The same regression must fail against the pre-fix
  binary at its success-versus-failure assertion.
- Extend the existing real FastAPI/PostgreSQL/LOCAL ArtifactStore journey rather
  than adding another broad fixture. Its canonical fixture provisions the ART
  resolver, uploads and activates a prerequisite guide, releases/claims/starts
  a task. Switch to its real manager, declare a new guide and use the built CLI
  to upload/replay the original. Verify persisted bytes/hash and changed-byte
  conflict; a submitter without manager authority is denied. Retain the existing
  assigned-document download/revocation proof. The fixture uses development
  authentication and scripted setup findings, not live Flow or model evaluation.
  Retained backend owner tests prove MinIO custody and scoped manager/lifecycle
  controls; this command does not introduce a second authorization engine.
- Run the full CLI process/API suite with real PostgreSQL, Go build/vet/module
  verify/tidy-diff, Ruff/format, links/stale wording/Commitrail and required hosted
  full Backend. No unit-test proliferation, coverage quota or weakened gates.
- Demonstrate a discriminating regression for transport replay or receipt
  binding against a deliberately defective binary.

## Review findings

Plan review made unconfirmed receipts explicitly non-successful. Implementation
review found overbroad current documentation saying the entire CLI could not
upload; those statements now name the read/declaration commands. Upload and
download reuse one unchanged ART hard ceiling. A compiled SHA-binding mutant
returned success for a forged receipt and failed the exact process regression;
this proves that assertion detects the defect rather than merely executing it.
External review additionally reproduced a changed local file reporting success
for its original-size prefix. Recheck the full original before confirmation;
size/mtime alone cannot detect a same-sized overwrite with restored mtime.
