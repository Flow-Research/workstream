# WS-CLI-001-51 — Claim and start from the contributor workbench

- Initiative: `WS-CLI-001`
- Durable disposition: `Planned`
- Intended merge outcome: Let a contributor deliberately claim and start exact tasks through the existing public API, with discoverable navigation and honest uncertain-outcome recovery.

## Intent

The merged -50 workbench is an observation interface, not a complete contributor
journey. The human found navigation difficult and missing actions made the UI
feel temporary. Main `f16dfe055` exposes working `api.Client.ClaimTask` and
`StartTask` and explicit CLI commands, but TUI `ReadClient` and `Model.key` do not
expose them. No backend prerequisite is needed. The existing real-API TUI drill
proves reads and fresh revocation only; it must not be relabelled mutation proof.

## Bounded change

Allowed: `cli/internal/tui/`, TUI wiring in `cli/internal/command/tui.go` and its
affected tests, focused existing CLI native HTTP/public-API tests and an opt-in
POST capture hook in their existing socket fixture, CLI README,
the single terminal design document, affected roadmap/initiative/index claims.
Reuse the existing typed mutation client, sanitizer, response validation and
backend authorization. No backend/client transport/CI/dependency changes.

Not allowed: upload/Submission/revision/Review/Finance mutations, automatic
chained actions, polling, credentials/history storage, generic operation journal,
shell execution, compatibility paths, new auth rules or weakening tests.

## Design and decisions

- Add visible `a actions` on freshly inspected Ready task or Mine Overview.
  Offer only Claim for observed ready work, Start for observed claimed Mine.
  Observed status determines UI relevance, never server authority.
  Gate both on exact freshly fetched `ContributorTaskDetail`, not row status;
  Mine rows carry assignment status (`active`), not task status (`claimed`).
- Require a caller-owned UUID replay key saved outside this session, matching
  the explicit CLI contract. Explain this requirement before entry. Do not
  generate a transient key or imply crash recovery exists. Reason is omitted
  consistently in this slice (JSON `{}` through existing client).
  The UI cannot verify external saving: require user input and an explicit
  save-warning acknowledgment at confirmation, with no generated fallback.
- Confirm exact action, actor, project, task, key and available locked terms;
  Enter in key entry only advances to confirmation. Only a deliberate `y` at a
  usable terminal dispatches one POST. No request on selection or resize.
- Freeze the packet while sending. Navigation/refresh cannot replace it or
  dispatch another action. Quit cancels the client request, not server effects.
  Unknown, malformed success and transport cancellation never mean rollback.
- Preserve unknown packet in the session, with explicit same-packet replay and
  inert CLI recovery arguments. No automatically retried POST; no new key after
  uncertainty. Session loss clears protected work; retained recovery references
  must not expose previously cleared descriptions/terms or bearer.
- Confirmed receipt and subsequent read are separate outcomes. Do not erase a
  successful claim/start because a refresh fails; do not automatically start
  after claim. Reauthorize through existing API on every write/replay.
- Use a separate write outcome handler, not `failed()`'s read-page reset.
  Bind returned task/project to the frozen packet and claim assignment contributor
  to the bound actor; the existing typed decoder does not check the latter two
  against the caller's selection. Any mismatch is unknown, never success.
  Complete canonical 4xx is a known denial of that request; transport, cancellation
  and malformed responses remain unknown. A denied replay cannot retroactively
  prove an earlier unknown request failed. Keep unknown history until a validated
  receipt resolves it. On 401/403/concealed 404, clear protected descriptions and
  terms, retaining only minimal inert replay references; session failure disables
  replay in this session. Pending writes consume navigation/refresh/action keys.
  Quit cancels the request and exits, never claims server rollback; the caller's
  externally saved key is the restart recovery contract, not an in-memory journal.
- Add visible direct collection shortcuts `1 Ready`, `2 Mine`, `3 Submissions`
  from ordinary list/detail views and reverse Tab navigation. Text entry,
  confirmations, pending operations and overlays must consume their own keys.
  Preserve current keys and exact-resource cancellation semantics.

The caller-owned key is an explicit initial limitation, not the desired final
consumer UX. Automatic crash-safe operation recovery needs a separately bounded
private-storage design; do not hide it in this action slice.

## Acceptance criteria

- Native TUI can inspect Ready, confirm claim, see receipt, inspect Mine, then
  separately confirm start. Exact assignment/locked lineage remains backend-owned.
- Decline, resize below minimum, repeated keys, read movement and text entry
  cannot cause a write. Different task/project/actor cannot receive a late result.
- Lost response retains original action/key and only explicit replay reuses it.
  Read failure does not manufacture rejection, rollback or confirmed success.
- Real signed public API/PostgreSQL native drill proves claim/start, exact-key
  replay, ownership and fresh revoked-authority rejection; preserve old GET-only
  drill. HTTP tests prove exact wire/no automatic retry and corrupt receipt.
  Use the separate ready task from `create_task`, not `_prepared_packet`'s already
  started task. Prove claim replay before start, then start replay before revoke:
  claim replay after progression may validly return state-conflict. Assert
  caller/project substitution is unknown and that a successful write plus failed
  read still shows the confirmed write receipt without restoring protected text.
- Go build/test/vet/race, native HTTP tests, layout/hostile text/download guards,
  links, wording and full hosted proof remain required. Add a discriminating
  hidden-confirmation/duplicate-dispatch regression; do not weaken old assertions.

## Evidence

Focused model regressions exercise confirmation, frozen request identity,
substituted receipts, denied replay, protected clearing, bounded paste and
cross-resource navigation. Native HTTP tests exercise the built binary and
exact POST bytes. The separate signed public-API drill exercises claim and
start, same-key replay and live grant revocation against isolated PostgreSQL;
the earlier GET-only drill remains unchanged. These are distinct proof
boundaries, not evidence of the remaining submission journey. Exact-head
execution and reviewer results belong in the PR trust summary.

Independent review exposed a late-read/session-denial interleaving: opening
replay while a refresh was pending could leave confirmation actionable after
the read blocked the session. Dispatch must recheck session and replay
eligibility, not rely solely on the earlier modal entry check. A focused
regression must reject the old dispatch behavior. Same-collection shortcuts
from detail must also return to the list rather than silently doing nothing.
